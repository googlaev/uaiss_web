## База данных

### Схема таблиц

```sql
-- Пользователи
CREATE TABLE users (
    user_id       INTEGER PRIMARY KEY AUTOINCREMENT,
    full_name     TEXT,
    login         TEXT UNIQUE,
    password_hash TEXT,           -- SHA-256 без соли
    role          TEXT DEFAULT 'employee',  -- 'employee' | 'admin'
    email         TEXT
);

-- Типы экзаменов (справочник)
CREATE TABLE exam_types (
    id       INTEGER PRIMARY KEY AUTOINCREMENT,
    name     TEXT UNIQUE,
    emoji    TEXT,
    duration INTEGER  -- срок действия в месяцах
);

-- Экзамены сотрудников
CREATE TABLE exams (
    id                        INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id                   INTEGER REFERENCES users(user_id),
    name                      TEXT,    -- название типа экзамена
    date                      TEXT,    -- дата сдачи, формат ДД.ММ.ГГГГ
    duration                  TEXT,    -- срок действия в месяцах
    notification_sent         INTEGER DEFAULT 0,  -- legacy
    month_notification_sent   INTEGER DEFAULT 0,  -- legacy
    week_notification_sent    INTEGER DEFAULT 0,  -- legacy
    exam_day_notification_sent INTEGER DEFAULT 0, -- legacy
    end_day_notification_sent INTEGER DEFAULT 0,  -- legacy
    last_notification_day     INTEGER DEFAULT 0   -- актуальный: последний отправленный интервал
);

-- Статусы сотрудников
CREATE TABLE user_status (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id    INTEGER REFERENCES users(user_id),
    status     TEXT,     -- '🤒 Больничный' | '✈️ Командировка' | '🏖️ Отпуск'
    start_date TEXT,     -- формат ДД.ММ.ГГГГ
    end_date   TEXT      -- формат ДД.ММ.ГГГГ | NULL (открытый статус)
);

-- FCM-токены устройств (опционально, если Firebase активирован)
CREATE TABLE fcm_tokens (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id    TEXT NOT NULL,
    token      TEXT NOT NULL UNIQUE,
    updated_at TEXT DEFAULT (datetime('now'))
);

-- users дополнительно содержит:
--   max_chat_id TEXT  -- chat_id в MAX, куда бот шлёт уведомления (NULL пока не привязан)
--   max_user_id TEXT  -- user_id отправителя в MAX (для справки)

-- Одноразовые коды привязки MAX-аккаунта
CREATE TABLE max_link_codes (
    code       TEXT PRIMARY KEY,
    user_id    INTEGER NOT NULL,
    created_at TEXT NOT NULL
);
```

### Особенности

- Миграции реализованы через `ALTER TABLE ... ADD COLUMN` в функции `check_and_fix_database()` — запускается при старте сервера
- В таблице `exams` поля `notification_sent`, `month_notification_sent` и пр. — **legacy**, не используются; актуальное поле — `last_notification_day`
- Даты хранятся как TEXT в формате `ДД.ММ.ГГГГ` — нет поддержки нативных SQL-дат

| Метод | Путь | Тело | Описание |
|-------|------|------|----------|
| GET | `/max/status` | — | `{enabled, linked, bot_username}` — включён ли канал и привязан ли аккаунт |
| POST | `/max/link-code` | — | Генерирует одноразовый код привязки (TTL `max.link_code_ttl_minutes`) |

| POST | `/max/webapp-auth` | `{init_data}` | Автовход для мини-приложения MAX: проверяет подпись `initData` (MAX Bridge) и, если этот MAX-аккаунт уже привязан, выдаёт JWT без логина/пароля. Если ещё не привязан — `{"linked": false}`, фронтенд показывает обычную форму входа |

Привязку можно завершить двумя способами:
1. Фоновый поток внутри самого бэкенда (`start_max_bot()` / `_max_bot_loop()`): пользователь отправляет боту `/link КОД`, поток находит код в `max_link_codes`, записывает `chat_id` в `users.max_chat_id`. Отдельного процесса запускать не нужно.
2. **Мини-приложение**: при входе по логину/паролю внутри MAX (`POST /auth/login` с полем `max_init_data`) бэкенд проверяет подпись initData и сам записывает `max_chat_id`/`max_user_id` — код вводить не нужно, достаточно один раз войти внутри MAX.

**Мини-приложение MAX** (`maxapp/index.html` в коде == `www/index.html`, та же SPA, что и в APK):
- Отдаётся бэкендом по адресу `https://bot.codle.ru/maxapp/` (`StaticFiles` на директорию `www/`, см. `test_py_original.py`, монтирование `/maxapp`)
- URL `https://bot.codle.ru/maxapp/` прописывается в настройках бота на `business.max.ru/self` → Чат-боты → бот → ⋮ → Настройки → URL мини-приложения
- На клиенте подключается `https://st.max.ru/js/max-web-app.js` (MAX Bridge), который даёт `window.WebApp.initData`
- Если initData есть и соответствующий MAX-аккаунт уже привязан — автовход через `/max/webapp-auth`; если нет — обычная форма логина, после первого успешного входа аккаунт привязывается автоматически
- Валидация подписи: `verify_max_init_data()` в `test_py_original.py` — `secret_key = HMAC_SHA256("WebAppData", MAX_TOKEN)`, затем `HMAC_SHA256(data_check_string, secret_key)` сверяется с полем `hash` (алгоритм идентичен Telegram WebApp, см. `dev.max.ru/docs/webapps/validation`)

## MAX-уведомления

Дополнительный канал уведомлений через мессенджер MAX (`botapi.max.ru`).

**Работает полностью внутри одного процесса** — при старте FastAPI-приложения (`start_max_bot()`, вызывается рядом с `start_scheduler()`) поднимается daemon-поток `_max_bot_loop()`, который long-polling'ом читает `botapi.max.ru/updates` и обрабатывает `/start`, `/link КОД`, `/фио ...`. Отдельный процесс/скрипт для этого запускать не нужно — если `max.enabled` выключен или `max.token` пуст, поток просто не стартует.

**Привязка аккаунта — три способа:**

1. **Мини-приложение MAX** (проще всего): пользователь открывает мини-апп UAISS внутри MAX и один раз входит по логину/паролю — бэкенд проверяет подпись `initData` и сам пишет `max_chat_id`/`max_user_id` (см. раздел «MAX-уведомления и мини-приложение» выше). При следующих открытиях — автовход без пароля.

2. **По коду** (надёжный): в приложении/веб-интерфейсе жмёт «Привязать MAX» → `POST /api/v1/max/link-code` → получает 6-символьный код (хранится в `max_link_codes`, TTL `max.link_code_ttl_minutes`, по умолчанию 15 мин) → пишет боту `/link КОД` → фоновый поток находит код в БД и записывает `chat_id` в `users.max_chat_id`. Код мог получить только тот, кто уже вошёл в приложение под своим логином/паролем, поэтому переписывает `max_chat_id` без дополнительных проверок.

3. **По ФИО/инициалам** (без захода в приложение): пользователь сразу пишет боту `/фио` (алиас `/иниц`) в одном из трёх форматов:
   - `/фио Гуляев Иван Павлович` — ФИО полностью
   - `/фио Гуляев И.П.` — фамилия + инициалы
   - `/фио ГИП` — слитные инициалы (первая буква каждого слова ФИО)

   `find_max_user_by_name()` ищет совпадение по `users.full_name`; при неоднозначности (несколько сотрудников с одинаковыми ФИО/инициалами) или отсутствии совпадения — просит уточнить. Этот способ слабее (личность не подтверждена паролем), поэтому если аккаунт **уже привязан к другому чату**, бот отказывает и просит сначала отвязать MAX в приложении — иначе кто угодно, зная чужие инициалы, мог бы перехватить чужие уведомления. Отключается флагом `max.allow_name_link: false` в `config.json`.

При следующей проверке `check_and_send_notifications_sync()` шлёт уведомления и в MAX, и на email (если оба заданы) — уведомление считается отправленным, если сработал хотя бы один канал.

**Включение канала:** в `config.json` секция `max.enabled: true` и `max.token: "<токен бота>"`. Без токена канал молча выключен (`send_max_message` возвращает `False`, эндпоинт `/max/link-code` отвечает 400).

## Email-уведомления

Алгоритм `check_and_send_notifications_sync()`:

1. Выбирает все экзамены пользователей с непустым email
2. Для каждого вычисляет `end_date = exam_date + duration_months` (через calendar.monthrange)
3. Если `days_left ∈ NOTIFY_DAYS` и `last_notification_day != days_left` → отправляет письмо и обновляет `last_notification_day`
4. Если `days_left < 0` и `last_notification_day != -1` → письмо о просрочке, ставит `-1`

> **Особенность:** Расчёт дат в уведомлениях использует `calendar.monthrange` (точный), а в `/exams/my` — умножение на 30 дней (приближённый). Это может давать расхождение ±1-2 дня.

## Безопасность — известные проблемы

| Проблема | Уровень | Рекомендация |
|----------|---------|--------------|
| SHA-256 без соли | Средний | Заменить на bcrypt/argon2 |
| CORS `allow_origins=["*"]` | Средний | Ограничить до домена приложения |
| SMTP-пароль в config.json | Средний | Переменная окружения |
| JWT без blacklist (logout не реален) | Низкий | Redis-blacklist или короткий TTL |
| Отсутствие rate-limit на `/auth/login` | Средний | slowapi или nginx limit |
